# Heaped & Stacked UI: guide for AI-assisted changes

A gym-themed learning app for programmers. Keep the codebase small and easy to read:
before adding a file, library or pattern, check whether an existing one already does the job.

## Vocabulary

The gym words are UI only. The API speaks of concepts and questions; keep it that way.

| UI (gym)                                | API (code)                                   |
| --------------------------------------- | -------------------------------------------- |
| muscle                                  | concept (owned by its author, `createdBy`)   |
| exercise                                | question                                     |
| load (1–10)                             | `difficultyScore`                            |
| set                                     | answer (`/learning/answers`)                 |
| your form (1–10)                        | `selfGrade`, from "poor form" to "nailed it" |
| felt like (1–10)                        | `perceivedDifficulty`                        |
| spot check                              | reviews (`/content/reviews`)                 |
| feedback, "▲ good one" / "▼ not great"  | reports (praise or problems) and votes       |
| "fixed it" / "dismiss"                  | report status `RESOLVED` / `DISMISSED`       |
| "open to all coaches"                   | `contributionPolicy` `AUTO_ACCEPT`           |
| "approve other coaches' exercises" (on) | `contributionPolicy` `OWNER_APPROVAL`        |
| benched                                 | question status `RETIRED`                    |
| head coach / gym staff / athlete        | role `ADMIN` / `STAFF` / `MEMBER`           |

Whether an exercise is accepted for a muscle (`PENDING` / `ACCEPTED` / `DECLINED`) is decided per
muscle by its owner. Don't show these states to users: owners see only what waits for them, in
the spot check.

## Structure

```
src/
  main.tsx            app start: React Query client + router
  router.tsx          every route, defined in code (no file-based routing), with its tab title (head);
                      a crashing page shows AppError (Layout.tsx)
  styles.css          design tokens (colours per theme, fonts), page backgrounds, pixel utilities
  labels.ts           how API values and scales are shown (policies, grades, report reasons)
  site.ts             the facts the footer pages state (owner, contact, hosting, coffee link)
  api/
    schema.d.ts       GENERATED by `npm run api:types`; never edit by hand
    types.ts          the types pages use (User, Concept, Question, Answer, Review, ...)
    client.ts         the only HTTP code: cookies, CSRF, errors (ApiError)
    queries.ts        one React Query hook per API use case
  mocks/              mock mode only (`npm run dev:mock`): a pretend API built with MSW
    data.ts           sample users, muscles, exercises and past sets, typed with the API types
    handlers.ts       one handler per API endpoint the UI calls, with the API's rules
    browser.ts        starts the mocks before the app renders
  components/
    Layout.tsx        top bar (nav buttons, theme switch), workout bar, page background, footer (links), 404
    WorkoutBar.tsx    the sticky "next workout" strip + useWorkoutMuscles (the picked muscles)
    RequireSignIn.tsx wraps pages that need a signed-in user
    ui.tsx            Button, Card, Stat, Field, Badge, PageHeading, ErrorMessage, Avatar, RichText, Logo, Pager, ...
                      indentOnTab (Tab indents in code textareas; Esc, then Tab moves on)
    LoadMeter.tsx     1–10 plate scales: LoadMeter (read-only) and PlatePicker
  pages/
    LandingPage.tsx       one-screen hero (picking muscles happens in the workout bar)
    PastWorkoutsPage.tsx  history: sets, calendar, top 3 muscles, recent sets
    LockerRoomPage.tsx    own account, behind the avatar in the top bar (name, sign out, delete)
    FrontDeskPage.tsx     admins only: the gym overview (a row of numbers), members, roles (athlete /
                          gym staff / head coach), blocking, deleting
    SitePages.tsx         the footer pages: About, Privacy, Terms, Code of Conduct, Contact. Keep the
                          privacy policy true to what the app does.
    coach/            Coach's Corner, in tabs (?tab=): add exercise, muscles, your exercises (with vote
                      totals), spot check, feedback; ?edit=<id|tag> turns the exercise or muscle form
                      into an edit
                      ExercisePage (/coach/exercises/<id>): one exercise for its author and staff, with its
                      votes, all its feedback and its actions; YOUR EXERCISES and FEEDBACK titles link to it.
                      Coach's Corner shows only to whoever may add content (`canContribute` on the current
                      user: staff, and members when the API's MEMBERS_CONTRIBUTE is on); members can still
                      edit what they wrote.
    rack/             ExerciseRack (the solve layout), TrainPage (/train, a workout), RackPage (author preview)
```

The exercise rack is one column of full-width cards (the author preview and the set review too),
in the order the athlete uses them. Rating the exercise sits on the exercise; grading the set sits
on the model answer. There is no separate feedback card. Every vote and plate click saves, with no
save button; a value gets a green "✓ SAVED" once stored, and clicking the chosen plate or vote
again clears it (also saved). Buttons sit on the left.
1. THE EXERCISE, with "▲ GOOD ONE · n" / "▼ NOT GREAT · m" top left, before its heading. Signed
   in (never in an author preview) they're the athlete's vote, from the start: their own one is
   green for ▲, amber for ▼.
   - right under the vote buttons, above the title: a note to its coach (optional, up to 2000
     characters, SEND), opened by either vote: praise after ▲, "what's off?" after ▼ (kind OTHER,
     shown as "not great"); taking the vote back closes it. No further options. One open note per
     exercise: once sent, YOUR NOTE shows it there with EDIT (then SAVE CHANGES / CANCEL) and
     WITHDRAW, also when the exercise comes back, until its coach decides it.
   - at the bottom of the card, FELT LIKE, how hard it felt: saved with the set, so it opens once
     the set is submitted
   Up votes and praise are likes: they make an exercise come up a bit more often. The author sees
   vote totals and feedback (Coach's Corner, FEEDBACK tab), never who voted or sent it.
2. YOUR SET (the answer editor): at least 60% of the screen height before submitting
3. after SUBMIT SET, a closed MODEL ANSWER card that opens only on SHOW MODEL ANSWER (the athlete
   thinks it over first). Open, it ends with HOW CLOSE WERE YOU?, the athlete's grade of their own
   set (optional), which shows their weak spots in Past Workouts
4. YOUR PREVIOUS SETS (earlier answers to the same exercise), once the model answer is shown
5. FINISH / NEXT EXERCISE

New parts of solving an exercise become new cards in the place they're used. Training questions
come without their model answer; it arrives with the saved answer.

The exercise form in Coach's Corner follows the same top-to-bottom order: TARGET MUSCLES, TITLE,
THE EXERCISE, MODEL ANSWER, LOAD, SOURCE, then PUSH on the left. THE EXERCISE and MODEL ANSWER are
each one full-width pane with WRITE / PREVIEW tabs. The field grows with its text (never an inner
scrollbar), and the preview keeps the field's height, so switching tabs doesn't make the page jump.

Every exercise has a short title (at most 120 characters): the heading of THE EXERCISE card and
what lists show, with the start of the text under it. Muscle tags (`#databases`) are set in the
body font: the pixel font is only for short uppercase headings and buttons, never small text.

Long text (exercises, model answers) is shown with `RichText`: line breaks are kept, lines of
` ``` ` fence code blocks (an optional language after the first becomes the label), and
`backticks` mark inline code, `**double asterisks**` bold. Authors get a live preview and a short
hint on the syntax.

Code blocks look like IntelliJ's Darcula editor in both themes: the `code-*` tokens in `styles.css`.
Blocks labelled `java` get syntax colours from `highlightJava` in `ui.tsx`: a single small regex
pass (comments, strings and text blocks, annotations, numbers, keywords, method names before `(`),
not a library. `HIGHLIGHTED_LANGUAGES` lists the languages with colours; other languages show as
plain code, and the exercise form's hint says so. To support a new language, add a highlighter
the same way and list it there.

## Rules

- **API calls:** pages never call `api` or `fetch` directly. They use a hook from
  `api/queries.ts`; add one there when a page needs a new call. Wrap calls in `call()` so errors
  become `ApiError` with the API's message. Server failures (5xx) show the API's request id as
  "ref …" in `ErrorMessage`, for bug reports.
- **Types:** use the types from `api/types.ts`, never hand-written copies of API shapes. After an
  API change: `npm run api:types`, then fix what `npm run typecheck` reports.
- **Auth:** the session is an HTTP-only cookie set by the API; the UI never sees or stores a
  token. Sign in = full-page navigation to `SIGN_IN_URL` (`signInAndReturnTo(path)` comes back to
  that page instead of the home page). The CSRF header is added by `client.ts`. Don't use
  localStorage for anything auth-related.
- **Visitors** may pick muscles and train: the workout bar and `/train` work signed out. Signed-in
  only queries take a `signedIn` flag so visitors never call them. Saving a set signs in first
  (SIGN IN & SUBMIT); everything else (past workouts, coach's corner, locker room) is behind
  `RequireSignIn`.
- **Styling:** Tailwind classes with the tokens from `styles.css` (`bg-paper`, `bg-card`,
  `text-ink`, `border-line`, `bg-pixel`, `bg-amber`, `text-faded`, `bg-danger`, `bg-code`) and the
  `ui.tsx` building blocks. No raw colour values and no component libraries; a new colour becomes a
  token, with a value for each theme.
- **Themes:** dark is the default, light the alternative (the switch in the top bar; the `dark`
  class on `<html>`, set before first paint by `index.html`). Tokens are roles, not colours:
  - `paper` is the page, `card` a raised surface, `ink` the text.
  - `line` is the bold borders (dimmer than the text in dark mode, so frames don't glare).
  - `shadow` is the pixel shadows, and `code` / `code-ink` are code blocks, dark in both themes.
  - The same classes work in both themes, so never pair a colour with a theme by hand.
  - Faint details use `ink` with opacity: borders as faint as `border-ink/20`, but text no fainter
    than `text-ink/70` (or `text-faded`), so it stays readable (WCAG AA, 4.5:1).
  - On amber, text is `text-on-amber` (dark in both themes); amber as text is `text-amber-ink`.
  - Don't dim a whole row or card with opacity: it dims its text and buttons too. Say the state in
    words instead (e.g. "draft").
- **Fonts and other files ship with the app** (fonts: Fontsource packages, imported in `main.tsx`).
  Never load anything from a third-party server: the Content-Security-Policy
  (`nginx.conf.template`) only allows the site itself, the API and GitHub avatars.
- **Style of the design:** pixel-flavoured, quirky programmer humour, gym puns, few elements per
  page, each one polished.
  - Cards, buttons, tabs and chips are square, with 2px `border-line` borders and offset shadows.
  - Form fields are the soft exception: thin borders, slightly rounded corners and a green focus
    ring (`inputClass` / `fieldFrameClass` in `ui.tsx`). Nothing else is rounded.
  - `font-display` (pixel font) only for short uppercase headings and buttons.
  - Colours are calm: a muted sage green for progress and success, amber for waiting, a soft red
    only for real problems, and no pure black or white.
- **Long lists** (YOUR EXERCISES, YOUR SETS, the front desk's members) show `PAGE_SIZE` (20) rows a
  page with `Pager` (PREV / NEXT, buttons on the left) under them. The API pages a list when the
  page needs only the rows shown (YOUR EXERCISES); when the page needs every row anyway (Past
  Workouts' stats, the front desk's filter), it cuts the pages itself. A new sort or filter starts
  again from the first page.
- **Buttons:** on the left, under what they act on (primary action first); status lines follow
  them. A closed card that waits for a click (SHOW MODEL ANSWER) shows the button in place of its
  heading.
- **Forms:** plain `useState` per field, a React Query mutation to submit, `ErrorMessage` for
  failures, a short `role="status"` line for success.
- **Layout:** pages use the width, up to `max-w-[96rem]`. Steps that happen one after another
  (solving an exercise, writing one) are stacked cards or fields in that order. Put things side by
  side on `lg` screens when they're read together (calendar | top muscles, a form | its
  explanation) and stack them on narrow screens. Short forms stay
  narrow (Locker Room: `max-w-3xl`). Every page has the same calm background (`bg-room` in
  `styles.css`: the page colour with a faint glow from the top, no patterns), so moving between
  pages never changes the room. `<main>` is a
  flex column, so a page can fill the height with `flex-1`. The landing page is one screen with no
  scrolling on desktop: the `short:` variant (windows up to 760px tall) scales it down.
- **Footer:** on every page: the spotter's note (AI / user content disclaimer), the motto,
  copyright and the site links (placeholders without `href` show as plain text until their page
  exists).
- **Checks before finishing:** `npm run typecheck` and `npm run format`.

Training: the workout bar (signed in, every page, sticky from `md` up) is the only place to pick
muscles. Order: label, + MUSCLES (fixed spot, never moves; shows how many muscles are hidden), then
the athlete's 5 most trained muscles as toggle chips (sets per muscle, then by name), plus any
other picked ones. + MUSCLES opens a filterable list of all muscles and "+ add a muscle". No
empty-state text: nothing picked = all muscles (said in the drop-down and START TRAINING's
tooltip). The pick lives in localStorage (a convenience; never anything auth-related). Don't show
"mixed"/"targeted" to users. A workout
serves one exercise at a time: SWAP EXERCISE skips it, SUBMIT SET saves the answer and reveals the
model answer, then NEXT EXERCISE or FINISH (to Past Workouts). The API picks each exercise
(`useNextExercise`, `GET /learning/questions/next`): new to the athlete first, then done ones at
random, weighted towards those done longest ago (never a fixed order). The workout sends every
exercise shown in the current round as `skip`; once all of the pick's exercises were shown, a new
round starts (leaving out the one just done). A workout never ends by itself and there's no
"workout complete": the athlete decides with FINISH. Changing the pick mid-workout keeps the
current exercise; the next one comes from the new pick. No timers. Past Workouts is about
history, not streaks.

Progress through the pick: above the rack, a line says whether the exercise is new and how many
new ones are left for the picked muscles (`unansweredCount` from the API, minus the one just done).
Finishing the last new one shows MUSCLE MAXED OUT: from then on, only repeats until coaches add
exercises. YOUR SET offers "start from the snippet" when the exercise has a code block (copies it
into the answer). Athletes write plain text: their sets are shown as typed, never as `RichText`.

The workout in progress survives leaving `/train`: TrainPage keeps it (current exercise, seen
ids, sets done, draft answer, submitted result) in the tab's sessionStorage, tied to the user, and
the top bar's TRAINING RACK button returns to it. A visitor's workout is adopted by the account
they sign in with, so the draft survives SIGN IN & SUBMIT. FINISH ends the workout and clears it.

New users: every place that needs a muscle explains what one is ("a topic to train") and links to
Coach's Corner's MUSCLES tab (`/coach?tab=muscle`): "+ add a muscle" in the workout bar's
drop-down and the exercise form's "+ missing a muscle?".

Managing content (Coach's Corner) shows only the actions the API allows the signed-in user, and
the API's message when it still refuses one:

| Action | Exercise (YOUR EXERCISES)                            | Muscle (MUSCLES tab list)                        |
| ------ | ---------------------------------------------------- | ------------------------------------------------ |
| EDIT   | author, staff                                        | owner, staff (the tag can't change)              |
| BENCH  | staff (status `RETIRED`), UNBENCH back               | (no retire button; bring back for retired ones)  |
| DELETE | staff, or the author of a draft; never once answered | staff, or the owner of a draft; never while used |

Edits reuse the add forms (`?edit=` + `key`), then return to the list. Deleting asks for
confirmation; benching and retiring don't, since they're undone with one click.

Artwork: the cast, the brain and the coffee mug, appears in one place only: the landing page,
which cross-fades through their 11 sprites (`CastCycle`).
- The sprites are true pixel art, 96 × 96 px on a transparent background, in `src/assets`.
- They're shown at exactly 3× (288px) or 4× (384px) and rendered `pixelated`, so every pixel stays
  square. Keep any new size an integer multiple of 96.
- They sit on the page with no frame and no glow: each has a light rim, so it reads on both themes.
- With reduced motion, the first picture stays. No sprites anywhere else.

Logo: `Logo` in `ui.tsx`, a barbell whose weights are code braces, {—}, on a 16-pixel grid (braces
`fill-pixel`, bar `fill-ink`, so it follows the theme), shown in the top bar. `public/favicon.svg`
is the same drawing, with colours for light and dark browser themes.

Mock mode: every API call the UI makes needs a handler in `src/mocks/handlers.ts`, answering like
the real API (same URL, same JSON, same `{"message"}` errors, same rules). When you add a hook to
`api/queries.ts`, add its handler in the same change. Mocks never ship: `main.tsx` only loads them
when `VITE_MOCK_API=true`, and app code must not import from `src/mocks`.
