# Heaped & Stacked UI: guide for AI-assisted changes

A gym-themed learning app for programmers. Keep the codebase small and easy to read:
before adding a file, library or pattern, check whether an existing one already does the job.

## Vocabulary

The gym words are UI only. The API speaks of concepts and questions; keep it that way.

| UI (gym)                                | API (code)                                                                  |
| --------------------------------------- | --------------------------------------------------------------------------- |
| muscle                                  | concept (owned by its author, `createdBy`)                                  |
| exercise                                | question                                                                    |
| load (1–10)                             | `difficultyScore`                                                           |
| set                                     | answer (`/learning/answers`)                                                |
| your form (1–10)                        | `selfGrade`, from "poor form" to "nailed it"                                |
| felt like (1–10)                        | `perceivedDifficulty`                                                       |
| TO APPROVE (APPROVE / ACCEPT / DECLINE) | reviews (`/content/reviews`); approve = accept + verify                     |
| verified (✓ VERIFIED), REVIEW, ✓ VERIFY | `verifiedBy` / `verifiedAt` (`/questions/{id}/verification`)                |
| sample set                              | `sampleSolution`                                                            |
| coach (who wrote an exercise)           | the question's `createdBy`                                                  |
| reviewer, reviewer mode                 | whoever may verify (`canVerify`); the UI's own switch (`asMember` when off) |
| gym muscle / community muscle           | concept `featured` true / false                                             |
| (members: every exercise) / TO VERIFY   | `pool` `ALL` / `TO_VERIFY` (`VERIFIED` exists, unused)                      |
| feedback, "▲ good one" / "▼ not great"  | reports (praise or problems) and votes                                      |
| "fixed it" / "dismiss"                  | report status `RESOLVED` / `DISMISSED`                                      |
| "open to all coaches"                   | `contributionPolicy` `AUTO_ACCEPT`                                          |
| "approve other coaches' exercises" (on) | `contributionPolicy` `OWNER_APPROVAL`                                       |
| benched (exercise), retired (muscle)    | question / concept status `RETIRED`                                         |
| head coach / gym staff / athlete        | role `ADMIN` / `STAFF` / `MEMBER`                                           |

Whether an exercise is accepted for a muscle (`PENDING` / `ACCEPTED` / `DECLINED`) is decided per
muscle by its owner. Don't show these states to users: owners see only what waits for them, in
the INBOX (TO APPROVE).

## Structure

```
src/
  main.tsx            app start: React Query client + router
  router.tsx          every route, defined in code (no file-based routing), with its tab title (head);
                      a crashing page shows AppError (Layout.tsx)
  styles.css          design tokens (colours per theme, fonts), page backgrounds, pixel utilities
  labels.ts           how API values and scales are shown (policies, grades, report reasons)
  site.ts             the facts the footer pages state (owner, contact, hosting, coffee link)
  api/
    schema.d.ts       GENERATED by `npm run api:types`; never edit by hand
    types.ts          the types pages use (User, Concept, Question, Answer, Review, ...)
    client.ts         the only HTTP code: cookies, CSRF, errors (ApiError)
    queries.ts        one React Query hook per API use case
  mocks/              mock mode only (`npm run dev:mock`): a pretend API built with MSW
    data.ts           sample users, muscles, exercises and past sets, typed with the API types
    handlers.ts       one handler per API endpoint the UI calls, with the API's rules
    browser.ts        starts the mocks before the app renders
  components/
    Layout.tsx        top bar (nav buttons, theme switch, the pixel coffee cup to Buy Me a Coffee), workout bar, page background, footer (links), 404
    WorkoutBar.tsx    the sticky "next workout" strip + useWorkoutMuscles (the picked muscles)
    RequireSignIn.tsx wraps pages that need a signed-in user
    ui.tsx            Button, Card, Stat, Field, Badge, PageHeading, ErrorMessage, Avatar, RichText, Logo, Pager, ...
                      indentOnTab (Tab indents in code textareas; Esc, then Tab moves on)
    LoadMeter.tsx     1–10 plate scales: LoadMeter (read-only) and PlatePicker
  pages/
    LandingPage.tsx       one-screen hero (picking muscles happens in the workout bar)
    PastWorkoutsPage.tsx  history: sets, calendar, top 3 muscles, recent sets
    LockerRoomPage.tsx    own account, behind the avatar in the top bar (name, sign out, delete)
    FrontDeskPage.tsx     admins only: the gym overview (a row of numbers), members, roles (athlete /
                          gym staff / head coach), blocking, deleting
    SitePages.tsx         the footer pages: About, Privacy, Terms, Code of Conduct, Contact. Keep the
                          privacy policy true to what the app does.
    coach/            Coach's Corner, built around duties (the API decides who may do what):
                      CoachsCornerPage (/coach?tab=): in reviewer mode MUSCLES (home: the muscles the user curates, each
                      with its workload, "54 exercises · 12 to verify · 2 waiting"; for staff also the
                      gym's pool and COMMUNITY, where they feature or retire members' muscles;
                      + NEW MUSCLE), EXERCISES (the user's own; the gym's pool for staff; + NEW
                      EXERCISE; ?muscle=<tag> opens it filtered), INBOX (TO APPROVE, then FEEDBACK;
                      its tab counts both). Coach's Corner is the back office: the work of checking
                      exercises happens on the rack (see "Curating" below).
                      MusclePage (/coach/muscles/<tag>): one muscle the user curates, its workload
                      and actions (EDIT MUSCLE, PUBLISH, FEATURE, RETIRE, DELETE, as allowed), then
                      THE WORK: TRAIN THE N TO VERIFY (a TO VERIFY workout on it), N TO APPROVE (the
                      INBOX) and SEE ALL EXERCISES (the EXERCISES tab on it); + NEW EXERCISE starts
                      on the muscle.
                      ExercisePage (/coach/exercises/new and /<id>): one screen to add or edit an
                      exercise: the form, its buttons in a sticky row at the bottom (SAVE & VERIFY /
                      SAVE, or PUSH & VERIFY / PUSH, for whoever may verify it), beside it TRY IT (a
                      workout with it first), votes, BENCH and DELETE, under it its feedback.
                      ?from=train|inbox|exercises or ?muscle=<tag> says where saving and cancelling
                      go back to.
    rack/             ExerciseRack (the solve layout), TrainPage (/train, a workout)
```

The exercise rack is one column of full-width cards (the set review too),
in the order the athlete uses them. Rating the exercise sits on the exercise; grading the set sits
on the sample set. There is no separate feedback card. Every vote and plate click saves, with no
save button; a value gets a green "✓ SAVED" once stored, and clicking the chosen plate or vote
again clears it (also saved). Buttons sit on the left.

1. THE EXERCISE. Signed in, the athlete rates it at the bottom of
   the card, under the exercise text, from the start, so rating needs no scrolling back up:
   - FELT LIKE, how hard it felt: saved with the set, so it opens once the set is submitted
   - under it, the vote: "▲ GOOD ONE · n" / "▼ NOT GREAT · m", their own one green for ▲, amber
     for ▼
   - right under the votes, a note to its coach (optional, up to 2000 characters, SEND), opened
     by either vote: praise after ▲, "what's off?" after ▼ (kind OTHER, shown as "not great");
     taking the vote back closes it. No further options. One open note per exercise: once sent,
     YOUR NOTE shows it there with EDIT (then SAVE CHANGES / CANCEL) and WITHDRAW, also when the
     exercise comes back, until its coach decides it.
     Visitors see the same vote buttons and counts in the same place; a click signs them in (the
     workout and draft carry on), and "// sign in to vote" says so.
     Up votes and praise are likes: they make an exercise come up a bit more often. The author sees
     vote totals and feedback (Coach's Corner, FEEDBACK tab), never who voted or sent it.
     A ✓ VERIFIED badge next to the heading when the exercise is verified. For staff, "edit exercise" next to it opens the exercise form
     (fix, verify, save) and comes back to the same workout, with the exercise as saved.
2. YOUR SET (the answer editor): at least 60% of the screen height before submitting. For a
   curator, on an exercise they may verify that isn't verified yet, REVIEW sits beside SUBMIT SET:
   the sample set at once, without answering; no set is logged ("// reviewed: no set logged")
3. after SUBMIT SET, a closed SAMPLE SET card that opens only on SHOW SAMPLE SET (the athlete
   thinks it over first). Open, it ends with HOW CLOSE WERE YOU?, the athlete's grade of their own
   set (optional), which shows their weak spots in Past Workouts
4. CHECKED IT? (CuratorCheck), under the open sample set, on the same exercises as REVIEW:
   ✓ VERIFY (verified, and on to the next exercise) and ✎ FIX (for whoever may edit it: the edit
   screen, then back to the workout; after SAVE & VERIFY in a TO VERIFY workout, straight on to
   the next exercise)
5. YOUR PREVIOUS SETS (earlier answers to the same exercise), once the sample set is shown
6. FINISH / NEXT EXERCISE

**Reviewer mode** (`components/ReviewerMode.tsx`, `useReviewer`) separates using the gym from
curating it. Whoever curates (staff, admins; later, members who own a muscle) gets a REVIEWER
switch in the top bar, next to the theme switch: `○ REVIEWER` off (the default), blue
`● REVIEWER` on. Off, they see exactly what a member sees: Coach's Corner with EXERCISES (their
own, + NEW EXERCISE) and INBOX (feedback on their exercises), every exercise to train on, the
plain rack. On, the curating comes in, and only then: MUSCLES (first tab) and muscle pages, the
gym's exercises and all feedback (the API's `asMember` is left off), approvals in the INBOX, TO
VERIFY in the bar, REVIEW / CHECKED IT? / "edit exercise" on the rack, SAVE & VERIFY, BENCH and
DELETE. Reviewer mode always trains TO VERIFY (a fixed label, no choice). A curator's
screen reached outside it (a muscle's page, someone else's exercise) shows `ReviewerModeNeeded`:
what it is, TURN ON REVIEWER MODE, BACK. It changes only what the screens show: the API's rules
are the same either way. New curating features go behind `reviewing`, never behind the role alone.

**Curating** (reviewer mode) is training with a check: START TRAINING is the one way into the work. A curator picks
muscles, switches reviewer mode on (or TRAIN THE N TO VERIFY on a muscle's page), then
per exercise: REVIEW, read, ✓ VERIFY or ✎ FIX. TO VERIFY serves the unverified exercises they may
verify, picked as in any workout (new ones first, at random), with "// to verify · N left". Verifying from a list without reading the
exercise isn't offered anywhere; APPROVE in the INBOX (fit and quality at once, for what others
submit) is the one exception.

New parts of solving an exercise become new cards in the place they're used. Training questions
come without their sample set; it arrives with the saved answer.

The exercise form in Coach's Corner follows the same top-to-bottom order: TARGET MUSCLES, TITLE,
THE EXERCISE, SAMPLE SET, LOAD, SOURCE, then PUSH on the left. THE EXERCISE and SAMPLE SET are
each one full-width pane with WRITE / PREVIEW tabs. The field grows with its text (never an inner
scrollbar), and the preview keeps the field's height, so switching tabs doesn't make the page jump.

Every exercise has a short title (at most 120 characters): the heading of THE EXERCISE card and
what lists show, with the start of the text under it. Muscle tags (`#databases`) are set in the
body font: `font-display` is only for short uppercase headings, labels and buttons.

Long text (exercises, sample sets) is shown with `RichText`: line breaks are kept, lines of
` ``` ` fence code blocks (an optional language after the first becomes the label), and
`backticks` mark inline code, `**double asterisks**` bold. Authors get a live preview and a short
hint on the syntax.

Code blocks look like IntelliJ's Darcula editor in both themes: the `code-*` tokens in `styles.css`.
Blocks labelled `java` get syntax colours from `highlightJava` in `ui.tsx`: a single small regex
pass (comments, strings and text blocks, annotations, numbers, keywords, method names before `(`),
not a library. `HIGHLIGHTED_LANGUAGES` lists the languages with colours; other languages show as
plain code, and the exercise form's hint says so. To support a new language, add a highlighter
the same way and list it there.

## Rules

- **API calls:** pages never call `api` or `fetch` directly. They use a hook from
  `api/queries.ts`; add one there when a page needs a new call. Wrap calls in `call()` so errors
  become `ApiError` with the API's message. Server failures (5xx) show the API's request id as
  "ref …" in `ErrorMessage`, for bug reports.
- **Types:** use the types from `api/types.ts`, never hand-written copies of API shapes. After an
  API change: `npm run api:types`, then fix what `npm run typecheck` reports.
- **Auth:** the session is an HTTP-only cookie set by the API; the UI never sees or stores a
  token. Sign in = full-page navigation to `SIGN_IN_URL` (`signInAndReturnTo(path)` comes back to
  that page instead of the home page). The CSRF header is added by `client.ts`. Don't use
  localStorage for anything auth-related.
- **Visitors** may pick muscles and train: the workout bar and `/train` work signed out. Signed-in
  only queries take a `signedIn` flag so visitors never call them. Saving a set signs in first
  (SIGN IN & SUBMIT); everything else (past workouts, coach's corner, locker room) is behind
  `RequireSignIn`.
- **Styling:** Tailwind classes with the tokens from `styles.css` (`bg-paper`, `bg-card`,
  `text-ink`, `border-line`, `text-blue`, `bg-blue-tint`, `bg-pixel`, `bg-amber`, `text-faded`, `bg-danger`, `bg-code`) and the
  `ui.tsx` building blocks. No raw colour values and no component libraries; a new colour becomes a
  token, with a value for each theme.
- **Themes:** dark is the default, light the alternative (the switch in the top bar; the `dark`
  class on `<html>`, set before first paint by `index.html`). Tokens are roles, not colours:
  - `paper` is the page, `card` a raised surface, `ink` the text.
  - `line` is the borders: dimmer than the text in both themes, so frames don't glare. Light mode
    is neutral cool greys in the spirit of Stack Overflow's light theme, dimmer than white: thin
    light frames and soft shadows, never dark outlines.
  - `blue` is selected and clickable: the current page or tab, the chosen side of a switch, links,
    focus rings, and the usual primary button (`Button` variant `ink`). Selected things sit on
    `bg-blue-tint` with `text-blue`; never a block of bright ink.
  - `pixel` (sage green) is progress, success and a page's main action (START TRAINING, SIGN IN,
    picked muscles, verified).
  - `shadow` is the offset shadows, and `code` / `code-ink` are code blocks, dark in both themes.
  - The same classes work in both themes, so never pair a colour with a theme by hand.
  - Faint details use `ink` with opacity: borders as faint as `border-ink/20`, but text no fainter
    than `text-ink/70` (or `text-faded`), so it stays readable (WCAG AA, 4.5:1).
  - On amber, text is `text-on-amber` (dark in both themes); amber as text is `text-amber-ink`.
  - Don't dim a whole row or card with opacity: it dims its text and buttons too. Say the state in
    words instead (e.g. "draft").
- **Fonts and other files ship with the app** (fonts: Fontsource packages, imported in `main.tsx`).
  Never load anything from a third-party server: the Content-Security-Policy
  (`nginx.conf.template`) only allows the site itself, the API and GitHub avatars.
- **Style of the design:** an editor's calm with a gym's humour: programmer jokes, gym puns, pixel
  art; few elements per page, each one polished.
  - One corner radius everywhere (`--corner`, 6px, set once in `styles.css`); tabs that sit on a
    line keep square bottom corners. Cards, buttons, tabs and chips have 2px `border-line`
    borders and offset shadows.
  - Form fields are the soft part: thin borders and a focus ring (`inputClass` /
    `fieldFrameClass` in `ui.tsx`).
  - One font, JetBrains Mono (IntelliJ's). `font-display` is its bold, spaced uppercase, for
    short headings, labels and buttons; `font-size-adjust` in `styles.css` keeps its sizes.
  - Colours are calm: ink blue for selected and clickable, sage green for progress and the main
    action, amber for waiting, a soft red only for real problems, and no pure black or white.
  - **Button sizes** (`buttonClass(variant, size)`, `Button size=`): lg for a page's main action,
    md for toolbar actions (+ NEW …, START TRAINING), sm for actions on a row or in a side panel.
    Never size a button with its own padding classes.
  - **Muscle kinds** show as a badge (`KindBadge`): GYM (blue) or COMMUNITY, DRAFT, RETIRED (muted),
    each with a tooltip. The gym's own muscles (`houseOwned`) always stay in the gym: no UNFEATURE.
  - **Words:** buttons are uppercase verbs (EDIT, VERIFY, BRING BACK); links are lowercase and
    blue; hints start with `//`, lowercase; tooltips are sentence case without a closing period,
    two parts joined with ":" or ";".
- **Long lists** (YOUR EXERCISES, a muscle's exercises, TO APPROVE, FEEDBACK, YOUR SETS, the
  front desk's members) show `PAGE_SIZE` (20) rows a
  page with `Pager` (PREV / NEXT, buttons on the left) under them. The API pages a list when the
  page needs only the rows shown (exercises, TO APPROVE, FEEDBACK; counts come from the totals); when the page needs every row anyway (Past
  Workouts' stats, the front desk's filter), it cuts the pages itself. A new sort or filter starts
  again from the first page.
- **Buttons:** on the left, under what they act on (primary action first); status lines follow
  them. A closed card that waits for a click (SHOW SAMPLE SET) shows the button in place of its
  heading.
- **Forms:** plain `useState` per field, a React Query mutation to submit, `ErrorMessage` for
  failures, a short `role="status"` line for success.
- **Layout:** pages use the width, up to `max-w-[96rem]`. Steps that happen one after another
  (solving an exercise, writing one) are stacked cards or fields in that order. Put things side by
  side on `lg` screens when they're read together (calendar | top muscles, a form | its
  explanation) and stack them on narrow screens. Short forms stay
  narrow (Locker Room: `max-w-3xl`). Every page has the same calm background (`bg-room` in
  `styles.css`: the page colour with a faint glow from the top, no patterns), so moving between
  pages never changes the room. `<main>` is a
  flex column, so a page can fill the height with `flex-1`. The landing page is one screen with no
  scrolling on desktop: the `short:` variant (windows up to 760px tall) scales it down.
- **Footer:** on every page: the coach's note (AI / user content disclaimer), the motto,
  copyright and the site links (placeholders without `href` show as plain text until their page
  exists).
- **Checks before finishing:** `npm run typecheck` and `npm run format`.

Training: the workout bar (signed in, every page, sticky from `md` up) is the only place to pick
muscles. Order: label, + MUSCLES (fixed spot, never moves; shows how many muscles are hidden), then
the athlete's 5 most trained muscles as toggle chips (sets per muscle, then by name), plus any
other picked ones; suggestions come from the gym's pool only. + MUSCLES opens a filterable list in
two groups, GYM (featured muscles, the gym's pool) and COMMUNITY (members' own muscles, picked on
purpose), and "+ add a muscle". No empty-state text: nothing picked = all the gym's muscles (said in
the drop-down and START TRAINING's tooltip). The MUSCLES tab lists YOUR MUSCLES, and for staff THE
GYM'S POOL and COMMUNITY, each with the actions the API allows: owners edit, publish, retire, bring
back and delete their own (once it's out of the pool); staff feature / unfeature, curate the pool,
and retire or bring back a community muscle. The front desk gives MEMBER or STAFF; ADMIN comes only
from the API's configuration. Its INVITES section lists who may sign in (none: anyone; any: only
them and head coaches). A refused sign-in comes back as `/?signInError=<why>` (`not_invited`,
`account_not_active`, else general), shown as an alert on the landing page. The pick lives in localStorage (a convenience; never anything auth-related). Don't show
"mixed"/"targeted" to users. Which exercises (`useWorkoutPool`, the API's `pool`): members
always train all of them (`ALL`), the checked ones marked ✓ VERIFIED on the rack; no choice (a
✓ VERIFIED / ALL chip was dropped before TEST, to keep the bar simple). In reviewer mode it's
always TO VERIFY, shown as a fixed blue label after the muscle chips. The `./train ... --to-verify`
prompt, the progress line (counts only in reviewer mode) and the empty rack (LEAVE REVIEWER MODE)
follow it. On the training rack, START TRAINING's place shows
"● TRAINING", the same width, so the bar never jumps. Two decisions, kept apart: fit is per muscle
(a muscle's curator accepts or declines an exercise added to it), quality is per exercise (verified:
checked once, whatever muscles it's on; `mayVerify` in api/types.ts says who: staff when it's on any
gym muscle, otherwise its muscles' owners). An edit by someone who can't verify it clears the check.
"verified" is the only word for quality; "approve" means accept and verify at once. A workout
serves one exercise at a time. Above the rack: SWAP EXERCISE skips it (NEXT EXERCISE once the set
is done), and ← PREVIOUS goes back to one moved past, with its draft or set as left (the last 20).
SUBMIT SET saves the answer and reveals the sample set, then NEXT EXERCISE or FINISH (to Past
Workouts). Past Workouts' calendar steps month by month (◀ ▶), back to the month of the first set. The API picks each exercise
(`useNextExercise`, `GET /learning/questions/next`): new to the athlete first, then done ones at
random, weighted towards those done longest ago (never a fixed order). The workout sends every
exercise shown in the current round as `skip`; once all of the pick's exercises were shown, a new
round starts (leaving out the one just done). A workout never ends by itself and there's no
"workout complete": the athlete decides with FINISH. Changing the pick mid-workout keeps the
current exercise; the next one comes from the new pick. No timers. Past Workouts is about
history, not streaks.

Progress through the pick: above the rack, a line says whether the exercise is new and how many
new ones are left for the picked muscles (`unansweredCount` from the API, minus the one just done).
Finishing the last new one shows MUSCLE MAXED OUT: from then on, only repeats until coaches add
exercises. YOUR SET offers "start from the snippet" when the exercise has a code block (copies it
into the answer). Athletes write plain text: their sets are shown as typed, never as `RichText`.

The workout in progress survives leaving `/train`: TrainPage keeps it (current exercise, seen
ids, sets done, draft answer, submitted result) in the tab's sessionStorage, tied to the user, and
the top bar's TRAINING RACK button returns to it. A visitor's workout is adopted by the account
they sign in with, so the draft survives SIGN IN & SUBMIT. FINISH ends the workout and clears it.

New users: every place that needs a muscle explains what one is ("a topic to train") and links to
Coach's Corner's MUSCLES tab (`/coach?tab=muscle`): "+ add a muscle" in the workout bar's
drop-down and the exercise form's "+ missing a muscle?".

Managing content (Coach's Corner) shows only the actions the API allows the signed-in user, and
the API's message when it still refuses one:

| Action | Exercise (YOUR EXERCISES)                            | Muscle (MUSCLES tab list)                        |
| ------ | ---------------------------------------------------- | ------------------------------------------------ |
| EDIT   | author, staff                                        | owner, staff (the tag can't change)              |
| BENCH  | staff (status `RETIRED`), UNBENCH back               | (no retire button; bring back for retired ones)  |
| DELETE | staff, or the author of a draft; never once answered | staff, or the owner of a draft; never while used |

Edits reuse the add forms (`?edit=` + `key`), then return to the list. Deleting asks for
confirmation; benching and retiring don't, since they're undone with one click.

Artwork: the cast, the brain and the coffee mug, appears in one place only: the landing page,
which cross-fades through their 11 sprites (`CastCycle`).

- The sprites are flat cartoon drawings, 384 × 384 px on a transparent background, in `src/assets`:
  the original 96 px pixel art, smoothed (Scale2x to 8×, each colour's region blurred and the
  strongest colour kept, then halved for anti-aliased edges), so the colours and shapes stay the
  same without a pixel grid. Shown at 288 or 384 px, with the browser's normal smoothing.
- A new sprite: draw it as 96 px pixel art in the cast's palette (artwork/characters in the
  workspace), then smooth it the same way.
- They sit on the page with no frame and no glow: each has a light rim, so it reads on both themes.
- With reduced motion, the first picture stays. No sprites anywhere else.

Logo: `Logo` in `ui.tsx`, a barbell whose weights are code braces, {—}, on a 16-pixel grid (braces
`fill-pixel`, bar `fill-ink`, so it follows the theme), shown in the top bar. `public/favicon.svg`
is the same drawing, with colours for light and dark browser themes.

Mock mode: every API call the UI makes needs a handler in `src/mocks/handlers.ts`, answering like
the real API (same URL, same JSON, same `{"message"}` errors, same rules). When you add a hook to
`api/queries.ts`, add its handler in the same change. Mocks never ship: `main.tsx` only loads them
when `VITE_MOCK_API=true`, and app code must not import from `src/mocks`.
